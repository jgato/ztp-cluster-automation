—— FOUNDATIONS

The Building Blocks

Kubernetes & OpenShift

Kubernetes is the standard for container orchestration. OpenShift builds on it with enterprise features: integrated CI/CD, operator lifecycle management, and multi-cluster capabilities.

For this talk: OpenShift = Kubernetes + Enterprise Services

GitOps Methodology

GitOps uses Git as the single source of truth for declarative infrastructure. The desired state is described in YAML files stored in a Git repository.

Add a file that defines a cluster → installs the cluster.
Remove the file → destroys the cluster.

—— CONTEXT

Bare Metal Clusters Need a Different Approach

Bare Metal at Scale

Telco and edge deployments require hundreds of OpenShift clusters on bare-metal servers. Each needs BMC configuration, ISO booting, and full OS installation.

RHACM & ZTP

Red Hat Advanced Cluster Management provides Zero Touch Provisioning via the Siteconfig Operator. A single ClusterInstance CR defines the entire cluster.

GitOps with ArgoCD

Git is the single source of truth. ArgoCD watches the repository and reconciles state. Adding a line to kustomization.yaml deploys a cluster.

—— THE PROBLEM

Manual Steps Slow Everything Down

RHACM manages clusters with ZTP GitOps. In practice, each operation still requires many manual steps.

Manual Steps Per Operation

  • Edit kustomization.yaml — comment or uncomment a line
  • Git commit and push the change
  • Sync the ArgoCD application
  • Monitor installation for ~45 minutes
  • If something fails, repeat from the top
  • Extract credentials when done

—— CLUSTERINSTANCE

One YAML Defines an Entire Cluster

apiVersion: siteconfig.open-cluster-management.io/v1alpha1
kind: ClusterInstance
metadata:
  name: sno1
  namespace: sno1
spec:
  baseDomain: example.com
  clusterNetwork:
    - cidr: 10.128.0.0/14
  nodes:
    - hostName: sno1.example.com
      bmcAddress: redfish://192.168.1.10/...
      bmcCredentialsName:
        name: sno1-bmc-secret
      bootMACAddress: aa:bb:cc:dd:ee:ff
      role: master
      # ... network config, disk hints, etc.

What This Defines

  • Identity: cluster name, domain, namespace
  • Network: cluster CIDR, service network, DNS
  • Hardware: BMC address for remote power control
  • Credentials: reference to BMC secret
  • Boot: MAC address, disk, NIC configuration

—— LESSONS LEARNED

Lessons From Teaching an LLM to Be Deterministic

Making It Deterministic

LLMs are not deterministic by nature. Non-deterministic behavior makes it hard to manage permissions and keep the agent under control. Sometimes it tries to solve problems it should not.

Scripts as Guardrails

Natural language defines the workflow steps. But when reliability matters, bash scripts provide deterministic execution. Not as elegant, but the agent writes them for you anyway.

Permission Management

You want to avoid *.* but also avoid being prompted at every step. Skills have their own allowed-tools scoping. Combine this with global settings for layered security.
