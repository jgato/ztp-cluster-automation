Background

Kubernetes & OpenShift

Kubernetes is the standard for container orchestration. OpenShift builds on it with enterprise features: integrated CI/CD, operator lifecycle management, and multi-cluster capabilities.

At the edge and in telco, clusters are deployed on bare-metal servers — no cloud provider, no VM layer. This means direct hardware management: BMC controllers, ISO booting, network bonding, and disk partitioning.

GitOps Methodology

GitOps uses Git as the single source of truth for declarative infrastructure. The desired state is described in YAML files stored in a Git repository.

A reconciliation engine (ArgoCD) continuously watches the repo and ensures the live cluster matches. Benefits:

  • Auditable: every change is a commit
  • Reversible: git revert undoes changes
  • Reproducible: same repo = same state
  • Collaborative: PRs for infrastructure

Context

Bare Metal at Scale

Telco and edge deployments require hundreds of OpenShift clusters on bare-metal servers. Each needs BMC configuration, ISO booting, and full OS installation — no VMs, no cloud APIs.

RHACM & ZTP

Red Hat Advanced Cluster Management provides Zero Touch Provisioning via the Siteconfig Operator. A single ClusterInstance CR defines the entire cluster: network, storage, BMC, and installation config.

🔄

GitOps Methodology

Git is the single source of truth. ArgoCD watches the repository and reconciles cluster state. Adding a line to kustomization.yaml deploys a cluster. Commenting it out removes it.

Architecture

🧠

Claude Code Skills

SKILL.md files define workflows as structured steps. Parent skills orchestrate child skills. The LLM handles adaptive decisions (monitoring loops), everything else is deterministic.

📜

Bash Scripts

Deterministic operations live in scripts with defined exit codes and key=value output. Pre-validation, secret management, credential extraction.

🔄

GitOps Loop

Every change follows: modify kustomization.yaml → commit → push → sync ArgoCD → monitor. The cluster converges to desired state.

Design Principle: Deterministic Where Possible, Intelligent Where Needed

Scripts handle mechanical operations (validation, secret creation, credential extraction). The LLM handles adaptive behavior (monitoring loops, user interaction, error reporting).

Redeploy & Secret Preservation

The hardest workflow: remove a cluster and redeploy it without losing credentials.

Backup secrets
→
remove_cluster
→
monitor removal
→
Restore NS + secrets
→
deploy_cluster

Secret Flow

  • Backup: oc get secret -o yaml to .temp/redeploy-<name>/
  • After removal: recreate namespace
  • Restore: oc apply -f from backup
  • Deploy detects existing secrets, skips zenity

Why It Matters

  • BMC credentials are entered once via GUI
  • Pull secrets come from user's auth.json
  • Without preservation, user re-enters everything
  • Redeploy becomes a one-command operation

My key learnings

🎯

Making the thing deterministic

LLMs are not detereministic by nature. A lot of headaches because of that. Not deterministic behaviour makes complicated: manage perms, have the agent under control (dont solve problems), etc

📁

Scripts are deterministic

I prefered to define the ToDos in natural language. But sometimes is better to specify the command as it is, or, to use scripts. Not so cool, but make your life easier. Anyway you will not code the scripts.

🔒

Manage Permissions

Painful, you dont want to allow *.* but you neither want to be asked in every step. Combine this with not deterministic commands. Skills have their own allowed-tool (still working on this).

🤖

Smartest agent

Sometimes the agent is too smart, and wants to solve probles they should not. You end-up tell him what to do, and WHAT NOT TO!!
