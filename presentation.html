Background

Kubernetes & OpenShift

Kubernetes is the standard for container orchestration. OpenShift builds on it with enterprise features: integrated CI/CD, operator lifecycle management, and multi-cluster capabilities.

For this talk: OpenShift = Kubernetes + Enterprise Services

GitOps Methodology

GitOps uses Git as the single source of truth for declarative infrastructure. The desired state is described in YAML files stored in a Git repository.

Add a file that defines a cluster → installs the cluster.
Remove the file → destroys the cluster.

Context

🖥

Bare Metal at Scale

Telco and edge deployments require hundreds of OpenShift clusters on bare-metal servers. Each needs BMC configuration, ISO booting, and full OS installation — no VMs, no cloud APIs.

🏠

RHACM & ZTP

Red Hat Advanced Cluster Management provides Zero Touch Provisioning via the Siteconfig Operator. A single ClusterInstance CR defines the entire cluster: network, storage, BMC, and installation config.

🔄

GitOps Methodology

Git is the single source of truth. ArgoCD watches the repository and reconciles cluster state. Adding a line to kustomization.yaml deploys a cluster. Commenting it out removes it.

My daily tasks, what to solve?

RHACM is a tool to use an Openshift cluster, to manage other Openshift/Kubernetes clusters (install, remove, configure, upgrade, etc).

  • Sync ArgoCD application

GitOps Flow

  • ClusterInstance CR defines the desired cluster
  • Push to Git triggers ArgoCD sync
  • ArgoCD applies CRs to hub cluster
  • Siteconfig Operator creates BareMetalHost, InfraEnv, AgentClusterInstall

One YAML Defines an Entire Cluster

apiVersion: siteconfig.open-cluster-management.io/v1alpha1
kind: ClusterInstance
metadata:
  name: sno1
  namespace: sno1
spec:
  baseDomain: example.com
  clusterNetwork:
    - cidr: 10.128.0.0/14
  nodes:
    - hostName: sno1.example.com
      bmcAddress: redfish://192.168.1.10/...
      bmcCredentialsName:
        name: sno1-bmc-secret
      bootMACAddress: aa:bb:cc:dd:ee:ff
      role: master
      # ... network config, disk hints, etc.

What This Defines

  • Identity: cluster name, domain, namespace
  • Network: cluster CIDR, service network, DNS
  • Hardware: BMC address for remote power control
  • Credentials: reference to BMC secret
  • Boot: MAC address, disk, NIC configuration

7 Automated Steps

  • pre-validate.sh — checks manifest & kustomization state
  • prepare_ztp.sh — namespace + secrets (or restore from backup)
  • Edit kustomization.yaml — uncomment cluster entry
  • Git commit + push
  • /sync_argocd — sync the clusters application
  • /visualize_cluster_status — monitor up to 3 hours
  • extract-credentials.sh — kubeadmin + kubeconfig

One command. Seven steps. ~45 minutes from YAML to running cluster.

7 Automated Steps

  • Backup secrets to .temp/redeploy-sno1/
  • /remove_cluster — full removal flow
  • /visualize_cluster_status — wait for NOT DEPLOYED
  • Recreate namespace if deleted
  • Restore secrets from backup
  • /deploy_cluster — full deploy (no credential dialog)
  • Report complete

Why It Matters

  • BMC credentials are entered once via GUI
  • Pull secrets come from user's auth.json
  • Without preservation, user re-enters everything
  • One command: full remove + redeploy cycle

My key learnings

🎯

Making the thing deterministic

LLMs are not detereministic by nature. A lot of headaches because of that. Not deterministic behaviour makes complicated: manage perms, have the agent under control (dont solve problems), etc

📁

Scripts are deterministic

I prefered to define the ToDos in natural language. But sometimes is better to specify the command as it is, or, to use scripts. Not so cool, but make your life easier. Anyway you will not code the scripts.

🔒

Manage Permissions

Painful, you dont want to allow *.* but you neither want to be asked in every step. Combine this with not deterministic commands. Skills have their own allowed-tool (still working on this).

🤖

Smartest agent

Sometimes the agent is too smart, and wants to solve probles they should not. You end-up tell him what to do, and WHAT NOT TO!!
